# ESP-Mosaico 首版设计

日期：2026-11-10。需求：[Issue #18](https://github.com/yangzhyo/red-green/issues/18)。状态：用户已确认设计并授权开工；实施与验收状态见 Issue #18 和实施计划，不以设计批准代替编译或真机验证。

## 用户已确认

- 实物为 **CoreBoard V1.2.1**，通过 USB-C 数据线长期连接这台 Mac，同时供电和通信。
- 主要同时使用 **1–5 个会话**。
- 屏幕采用 **主角＋总览**：左主角 **61.8%**、右总览 **38.2%**，按黄金比例分栏。
- mosaico 的 red-green 应用可用时，宠物、用量表和叫声全部在设备上；不可用时自动恢复电脑端。
- 首版只看宠物状态、用量和听叫声。**不增加设备端触摸、按键业务操作、点宠物聚焦终端、手动切换、静音或音量调节。** 硬件原有电源及维护按键仍由系统固件负责。
- 电脑继续采集会话与用量并判断状态；设备本地显示和播放预置声音。接管需应用就绪握手和心跳；重连同步现状，不补叫旧事件。

布局方向与左右比例已经确认；下文轮播、超时、像素间距和技术选型仍是设计者给出的默认方案，不冒充用户已经逐项选择。

## 目标与边界

保留 red-green 的“一会话一宠物”、三套皮肤、六种会话状态、按项目分配皮肤和叫声语义，让设备成为电脑旁的状态显示端。设备不运行 Claude Code/Codex，不接收对话正文、账号凭据、工作目录、tty 或终端操作指令。

首版支持一台 Mac 对一台 mosaico，连接仅为 USB。不做 Wi-Fi、蓝牙、云服务、远程控制、固件自动更新、触摸交互、传感器玩法或通用 USB 副屏。电脑端降级后的点击、拖动、用量表切换等既有操作保留。

自动回退以 **Mac 醒着且 red-green 主进程可运行** 为前提。Mac 睡眠或应用整体退出时，设备停止展示过期状态并静音；不能承诺此时电脑仍能输出。恢复后重新握手。

## 屏幕方案

**已确认决定（2026-11-10）：** 用户经 Demo 比较后选择「主角＋总览」，左主角 61.8%、右总览 38.2%。替代初稿中的五宠同屏网格。[比较与决定](2026-11-10-esp-mosaico-layout-options.md)保留选择过程；比例按扣除外边距和栏间距后的可用宽度计算。

目标画布为 480 × 480，延续现有像素宠物和深色壳体、绿/琥珀/红用量灯色。设备没有导航栏、可点击按钮或交互提示。

### 常驻画面

- 顶部约 128 像素留给共用用量表：左侧双环圆表，右侧来源/额度组、各窗口已用比例与重置时刻。只有一个窗口时不捏造第二窗口。
- 下部采用 **主角＋总览**。左侧显示一只放大的宠物、气泡、项目名和状态，右侧固定列出 1–5 个会话的项目名及状态；当前主角有位置标记。屏幕底部保留当前来源、会话位置和待处理数量。
- 左右比例固定为 **61.8 / 38.2**。当前 Demo 使用左右各 16 px 内边距、12 px 栏间距，剩余 436 px 分为约 269 px / 167 px；固件按可用宽度同比取整，误差不超过 1 px。少量会话时仍保留该分栏比例。
- 宠物和总览均有状态文字，不靠颜色独自表达状态。运行中沿用动词气泡，其他状态使用状态图示。总览字号不因会话数量或左右比例缩小。
- 总览按稳定会话顺序显示，不因主角切换或紧急度重排。输出端切换不重置会话身份、皮肤和已阅状态。
- 同项目、同来源的多个会话在名牌旁增加稳定短编号，避免相同皮肤和项目名无法区分；编号仅用于显示，不影响皮肤哈希。
- 项目名超出单行时自动缓慢滚动，完整名称最终可见，不依赖悬停或触摸；总览与主角名牌均适用，状态始终固定。当前网页原型使用截断，固件仍需实现长名称策略。
- 主角按 #25 用户确认每 6 秒轮换，对应色块完整闪烁两次；待确认、异常中止、轮到你优先，同级轮播。新状态与叫声即时更新，主角选择等轮次结束，不中途抢占；每四次选择插入一次全体公平轮播，多会话不连选同一只。切换主角不发声、不构成已阅；删除/失联立即清理。
- 超过五个会话时，总览按稳定顺序每页最多五个、随主角切换到对应页（#25），保留页码与总会话数；所有会话仍参与主角调度和叫声裁决。1–5 个的主要场景不分页，不静默丢弃更多会话。

### 用量无需操作

- 只有一个来源/额度组时固定显示；多个时每 **8 秒**自动轮播，来源与额度组名称随数值一起切换。
- 顺序采用现有默认优先级：Codex 默认组、其他 Codex 组、Claude；当前项仍存在时保持到本轮结束，不因每次快照重置计时。
- 每次显示最多两个窗口，超过两个则按窗口对继续轮播；圆表外圈/中心对应当页第一窗口，内圈对应第二窗口。标签使用真实窗口时长，不固定假设都是 5h/7d。
- 重置时刻由电脑按其时区格式化，显示日期及时间（当天可省日期），设备不另行联网校时。
- 缺失、非法或已过重置时刻的数据为“未知”或“已过期”，不当作 0%。有该来源会话但无可用数据时保留未知项，避免用户误认为没有用量。
- Codex 沿用成功快照 120 秒时效。Claude 的 `updated_at` 是**数值最后变化时间**，不是轮询成功时间：不能仅凭 120 秒没变化判为断流。首版显示“数值更新于 …”，到 `resets_at` 后转未知；无可信重置时刻则保持未知。此限制在安装说明中写明。
- 此有效性投影在电脑完成。设备端不重新解释各来源原始数据；桌面端现有 Claude 归零/隐藏规则在本次保持兼容，不借设备适配修改既有桌面行为。
- 无会话时显示“暂无会话”，隐藏用量与宠物，不叫。会话重新出现后自动恢复画面。

### 未接管时

设备正常运行但没有有效输出授权时，仅显示“等待电脑连接”，无旧宠物、旧用量或叫声。握手不兼容时显示“需要更新设备应用”。这些画面不代替电脑输出，不需要用户在设备上点确认。

## 状态、已阅和声音

电脑仍是唯一状态判断方。设备收到的是经已阅处理后的会话状态、皮肤、项目名和用量视图；不读取终端、不自行判断“看过了没有”。

- 用户在电脑聚焦对应终端后，已完成/异常中止按现有规则变为空闲；轮到你持续到真正回答。
- 前台静默照旧：当前正看着的会话不叫，其他会话照常。设备展示或用户看向设备，不构成已阅。
- 复用现有三皮肤 × 四发声状态的 12 个预生成 WAV。设备固定合理响度，保留不同状态的相对紧急程度；不加音量界面。现有 WAV 为 44.1 kHz 单声道、最长约 0.52 秒，实施时可离线转换为选定 codec 支持的等价格式。
- 同时到达的设备叫声串行播放，优先待确认、异常中止、轮到你、已完成；同优先级按事件顺序。超过 2 秒仍未开始的叫声丢弃，不排成长串过时提醒。
- 每次可发声转移产生唯一事件 ID，目标输出端在接收前即固定；对“已投递但是否响过不确定”的事件不改投另一个输出端、不在重连时重试。
- 保证同一事件不双播；设备在投递后立即崩溃等边界可能少响一次，持续可见的状态负责兜底。首版不承诺跨崩溃的声音恰好一次送达。
- 收回授权时立即清空设备声音队列并停止正在播放的叫声；接管前停止电脑正在播放的叫声。仅改变输出位置不产生状态转移事件。

## 自动接管与回退

电脑上的常驻采集和状态模型一直运行，隐藏宠物窗口不等于退出应用。USB 识别、下载模式或其他 Idea 都不能独自触发接管。

| 阶段 | 电脑输出 | 设备输出 | 进入/离开条件 |
|---|---|---|---|
| 电脑模式 | 正常 | 等待画面、静音 | 默认状态；识别到正确设备后可准备 |
| 准备接管 | 正常 | 后台装载快照，等待画面 | 校验应用/协议/资源版本，屏幕和音频初始化成功，完整快照已应用 |
| 交接 | 暂停新叫声，隐藏宠物和用量表，停止本地声音 | 尚未显示业务画面 | 电脑确认输出已停止后才发有效授权 |
| 设备模式 | 隐藏、静音 | 宠物/用量/叫声 | 设备取得有效授权并持续续期 |
| 回退 | 等待授权安全到期，然后恢复 | 到期清空业务画面并静音 | 断连、健康检查失败、版本失配或主动退出 |

正常数据变化尽快推送；已有来源的采集节奏（如 Codex 约 1.5 秒）不因 USB 而提高。稳定接管前要求正确应用完成两次间隔约 500 ms 的健康回应，避免枚举抖动导致频繁切换。

**默认时间预算：** 设备每 500 ms 请求续期，每次授权最长 2 秒；电脑在最后一次可能有效的授权发出后至少等待 2.5 秒，再恢复输出。正常回退以约 3 秒内恢复为验收目标，允许短暂静默以避免双播。重连准备期间电脑继续输出。

不能用“心跳断了，电脑立刻响”实现独占。设备可能还在运行、甚至还由电池供电；单向丢包时也要确保其授权结束。

### 授权时序约束

- 采用设备发起的有时限请求：设备创建随机 nonce 时即设置本地单调时钟截止时间 `请求创建 + 2秒`；延迟收到的授权不能从收包时重新计满 2 秒。
- 电脑回复绑定设备启动 ID、连接代次、nonce 和快照版本的授权，并记录自己的最迟发送时刻。设备只接受尚未到期且匹配当前请求的授权。
- 设备请求必早于电脑发出该授权，因此电脑等待“最后发送 + 2.5秒”可给设备的 2 秒期限留出传输方向与时钟误差余量。禁止传输层延后重放已失效授权。
- 续期确认必须经过实际显示/音频任务的健康检查；串口线程活着但渲染停滞，不能续期。授权到期的清屏/停声检查由高优先级看门任务执行；系统整体失去调度时由硬件看门狗复位，启动默认等待、静音。硬故障下的时限以真机验证为准，不宣称软件能证明物理屏幕或扬声器永不失效。
- Mac 睡眠唤醒、应用重启、设备重启都创建新代次并静默同步。电脑进程重启后在恢复桌面输出前也等待一个 2.5 秒安全窗口，以覆盖上个进程可能留下的授权。
- 状态模型超过 3 秒未提交“仍在正常处理”的更新时，停止续期；若电脑主进程本身异常，设备必须自行到期。

## 软件结构与技术选择

应用不是 macOS 扩展显示器，不传连续屏幕帧或系统音频。官方 USB 副屏示例依赖 Windows 驱动，本项目采用小量结构化消息与设备本地呈现。

### 电脑端

保留现有 Claude/Codex 观察链路与 manager 的状态/皮肤/已阅判断，增加一个集中管理输出的 **Module**。它的 **Interface** 接收完整显示快照与一次性叫声事件，并报告当前输出状态；窗口管理、声音停止、USB 识别、重连和授权时序隐藏在实现内。

这个 **Seam** 下有两个真实的 **Adapter**：桌面窗口/本地声音，以及 USB/mosaico。manager 不再分别直接调用两个输出端，也不在隐藏窗口中新增 JS 心跳定时器。定时、授权和 USB I/O 由 Rust 常驻循环承担，避免 WebKit 挂起隐藏窗口定时器。

桌面 Adapter 复用既有创建/隐藏/销毁窗口能力；进入设备模式时隐藏而保留状态，期间新会话不闪出窗口。回退时按当前完整快照对账，已结束的会话不能复活。窗口隐藏失败则中止接管。旧本地播放进程可被准确停止，不能仅继续使用不保留句柄的 `afplay` 调用。

设备 Adapter 不传播对话摘录、路径、tty 和凭据。会话身份使用 opaque ID，项目名允许 Unicode；消息有长度上限、版本和有效性校验。

### 设备端

设计者选型：**ESP-IDF + C/C++ + 官方 ESP-Mosaico BSP + LVGL**，参考官方 `hmi_demo` 和音频示例；应用侧拥有原生 USB 的 CDC 数据通道。电脑使用 macOS 标准串口设备访问这一通道，不依赖额外 Python Gateway 常驻。

USB 数据协议与日志隔离：生产 CDC 仅输出带类型与长度的业务帧；调试日志走独立调试通路或明确的日志帧，不混入任意 printf。保留识别/健康诊断消息，但首版不通过此业务通道刷固件。ESP-Iris/Vibe 可用于开发安装与诊断，不作为首版桌面运行依赖；不能让开发工具和 red-green 同时占用同一个 USB 接口。

固件工程放在独立的 `firmware/mosaico` 构建单元，设备工具链不进入日常桌面构建依赖。安装和 SDK 环境步骤在实现时记录。依赖锁定到经验证的 IDF/BSP/USB/LVGL 组合，不能把最新 BSP 与另一个工作区固定的旧 IDF 任意混装。

### USB 消息的语义

| 消息 | 必需语义 |
|---|---|
| Hello / Ready | 设备稳定 ID、boot ID、应用 ID、协议版本、资源版本、硬件识别、屏幕/音频健康；不能用串口路径充当身份 |
| Snapshot | 递增版本、完整会话列表/稳定槽位/状态/皮肤/名牌、用量视图、时间展示字段；先完整校验，再原子替换 |
| Applied | 已提交给显示任务的快照版本及健康信息；不是仅 USB 收到数据 |
| Lease request / Grant | 绑定启动与连接代次、有时限 nonce、授权的快照版本；遵守上述设备请求截止时间 |
| Call | 唯一事件 ID、会话 ID、皮肤/状态或资源 ID、有效期限、所属授权代次；无有效授权不播放 |
| Release / Health | 主动交回输出或报告失效；丢失这些消息也能靠授权到期安全回退 |

握手后发送完整快照；后续状态变化仍用完整快照，避免首版引入增量补洞。设备保留当前最新快照，丢弃旧版本及旧代次数据。小量状态不需要视频编码、压缩或网络服务器。

帧编码、串口库、LVGL 对象组织、字体子集和离线资源工具由实施者选择；必须满足以上 Interface，不需要为这些细节再次访谈用户。解析器有上限，超长/损坏数据不导致设备重启或读取越界；尺寸不足以容纳一个完整快照时保持电脑模式并记录诊断，不截断会话列表后假装就绪。

### 资源一致性

三套皮肤与六状态从现有精灵定义导出，保留状态的动作含义；CSS 的跳跃、探头、呼吸等运动参数在资源导出契约中显式记录，不能只取静态首帧。叫声沿用同一源文件，转换可重跑。设备无需 JS 引擎。

预置必要字体和状态图示。项目名不能因缺字变成方框；字体覆盖方案和内存占用需要用真实中英文项目名验证。资源包带版本/哈希，与应用协议共同参与 Ready。无匹配皮肤或叫声时不接管，而不是先把电脑隐藏。

## 硬件与验证门槛

用户的 **V1.2.1** 是实物版本；官方当前 BSP 公共枚举仅有 V1.0 / V1.2，不能直接据字符串相近就断言兼容。首先读取设备版本及 eFuse，核对官方 V1.2 映射并验证显示、音频和 USB。无法识别时停止设备初始化，电脑继续运行，不自行写 eFuse 或套 V1.0 引脚。

正式开发前的第一条技术验证路径是：锁定 SDK/BSP → 只读识别硬件与分区 → 构建最小屏幕/预置叫声/USB 握手样例 → 在实物核实控制线、重新枚举和断连行为。保留现有 Vibe/维护分区；首次安装前确认分区方案和可恢复的官方固件，不执行全片擦除或自动覆盖不明分区。

目前只完成文档和源码调研；未验证 V1.2.1 的实际板型编码、音频响度、USB 稳定性、字体可读性或持续运行。这些是计划中的验证门槛，不是要求用户现在回答的产品问题。

## 验收与测试策略

主要测试面是输出 Module 的 Interface：注入快照、叫声事件、单调时钟和模拟设备，观察桌面/设备 Adapter 的实际输出。内部只对有风险的帧解析与授权状态机补针对性测试，不测试一层层转发函数。

1. 注入 1–5 个会话，三种皮肤和六状态均有覆盖；左侧主角与右侧总览按 61.8/38.2 分栏，总览五个会话同屏且文字互不覆盖。主角动画、名牌、来源和总览标记一致。验证超过五个时总览分页不丢会话，轮播不构成已阅或触发叫声。
